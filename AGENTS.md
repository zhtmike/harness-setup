# Working in this repo

Personal harness setup guides — one `<harness>/README.md` per harness. A new harness gets a new directory; a retired harness's directory gets deleted, and the commit message says so (outside links may point here).

- Guides document personal machine setup: verify a claim against the harness's official docs before changing it — staleness fixes land in their own commits, never folded into unrelated changes.
- MCP claims verify against the live surface, not docs alone — `pi mcp list` for the registered tool surface, a codemode probe call for result shapes; only the live listing proves what registers today (gh retired `get_review_comments` into a `pull_request_read` method with no signal reaching the guide).
- AGENTS.md payloads are policy, not reference — routing precedence, selection order, dispatch policy, usage conventions that no live surface (tool declaration, skill description, config file, session-injected listing) self-describes. Capability enumeration, API shapes, config state, and model ids never enter a payload (tier by role, never by model id); each fenced payload stays ≤ 2,500 bytes and additions displace — surfaces update themselves, payloads only go stale.
- Context layers, one question each: AGENTS.md payloads say which and when (always loaded, every session and lane); zhtmike/skills bodies say how (on trigger, specializing a payload's tiering for their task class, never restating triggers or mechanics); pi-minimal-dispatch says what (generic mechanics for any user — tool schemas are always-loaded context and stay lean, docs read on demand; personal policy never enters). A layer restating another layer's answer is drift in the restating layer. The skills repo's side is already stated in its own CONTRIBUTING; no symmetric text here beyond this rule.
- Guides are version-free — content documents the harness's current release and carries no "since X.Y" dating; which release a claim was verified against is commit-message provenance, never guide content.
- Steps are self-contained and reproducible — each carries its full payload inline (commands, config blocks to paste); a combined whole-file example may repeat step payloads, but a step never delegates its payload to a forward pointer.
- Payloads stay minimal — config blocks carry exactly the keys and lines the tool consumes; whatever serves the human or the editor instead of the tool stays out of the payload, a prose note carries it instead.
- Skill rosters track zhtmike/skills — when that repo adds, removes, renames, or splits a skill, every guide's symlink step and skill checklist update in the same change; the h800-* cluster skills are deliberately out of the harness guides and join a roster only on explicit request.
- Placeholders only — `<YOUR_TOKEN>` / `${ENV_VAR}` forms. Never a real token, in content or in history.
- The shared spine (install → providers → MCP servers → AGENTS.md guidance → skills → verify) is deliberate; keep new guides on it where it applies.
- Cross-guide payload syncs copy semantics, never machinery: the shared workflow law (stage flow, wind-down, closure) is harness-agnostic and syncs across guides; the mechanics diverge because the harnesses do — pi has no sub-agents (artifact files into a fresh session, dispatch lanes), OpenCode delegates to native subagents. A sync carrying the other harness's mechanics into a guide is drift, not a sync.
- Machine profiles live in `machines/` — one payload-pure doc per machine, harness-agnostic wording, loaded verbatim into agent context; install notes and non-default local state belong in `machines/README.md`, never in the payload. Harness guides stay machine-neutral.
- Install steps reference the payload doc rather than inlining it — the one deliberate exception to the no-forward-pointer rule, because inlining the payload is the drift this structure exists to prevent.
- Support scripts live in `scripts/` — installed by symlink from their canonical location, with install notes in `machines/README.md`.
- Commit messages carry the why — the gists these came from had empty messages; that gap is the reason this repo exists. Content is docs: guide edits use the `docs` type.
- Commit messages describe guide changes only — no quoted user instructions, session habits, node-sync narratives, or local paths beyond the guides' own content; machine wiring is local state.
- Commits go through the fresh-review gate (the global commit-gate skill); draft the full message first. The owner pre-approves commits and pushes to this repo's own remote for their own sessions — present the diff and message for the record, run the fresh review, and proceed without waiting for a per-commit go.
